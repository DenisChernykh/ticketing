# Analytics

Сервис хранит продажи мероприятий и дневную выручку организаторов в собственной PostgreSQL. Две независимые Kafka consumer groups читают подтверждения, отмены и возвраты: `events` обновляет продажи мероприятий, `daily` — суммы по календарным дням UTC. Обе проекции получают каждую продажу.

HTTP API запускается вместе с consumers. Swagger доступен на `/docs`. `/health/ready` проверяет PostgreSQL; `/health/workers` отдельно показывает готовность, поколение и ошибку каждого consumer. При недоступной Kafka уже построенные отчёты остаются доступны, а подключение восстанавливается в фоне.

Внутренние маршруты требуют `X-Internal-Token`:

| Маршрут | Результат |
| --- | --- |
| `GET /internal/reports/events?organizerId=<uuid>` | Продажи мероприятий и место по количеству билетов |
| `GET /internal/reports/daily?organizerId=<uuid>` | Продажи по дням и накопленная выручка |
| `GET /internal/reports/popular?organizerId=<uuid>&limit=10` | Рейтинг из Redis sorted set с проверкой по PostgreSQL |
| `POST /internal/replay` с `{"projection":"events"}` | Новое поколение выбранной проекции; также поддержаны `daily` и `all` |

Sales проверяет пользовательскую сессию и роль организатора до вызова этих маршрутов и передаёт подтверждённый идентификатор. Analytics не подключается к БД Sales.

Receipt, состояние заказа в `projection_orders`, разница его вклада в агрегат и revision поколения коммитятся одной SQL-транзакцией. Более старое состояние не применяется поверх нового. Kafka offset подтверждается после коммита. Повтор сообщения не увеличивает счётчики. Изменённое содержимое под прежним идентификатором, неверный Kafka key или некорректное событие останавливают соответствующий consumer с видимой ошибкой; offset такого сообщения не подтверждается.

Рейтинг Redis хранится отдельно для каждого организатора и поколения. Полное обновление использует абсолютные `ZADD`, а замена всех участников и revision атомарна. Периодическое восстановление берёт значения из PostgreSQL. Неполные, устаревшие и недоступные данные Redis приводят к чтению результата из PostgreSQL.

Replay управляется тем же процессом, который владеет consumers. Он останавливает выбранную старую группу, фиксирует верхние offsets трёх партиций и строит новое поколение отдельной группой с начала истории. На границе каждая партиция приостанавливается. После полного пересчёта SQL-транзакция переключает active generation; та же новая группа продолжает live-чтение с сохранённых offsets. Продажи во время replay продолжаются. Старое поколение сохраняется; при ошибке переключения нет. `all` запускает два независимых перестроения, поэтому успешная проекция может переключиться, даже если вторая завершилась ошибкой.

```sh
pnpm --filter @ticketing/analytics start
pnpm --filter @ticketing/analytics replay events
pnpm --filter @ticketing/analytics replay daily
pnpm --filter @ticketing/analytics replay all
```

У локального topic три партиции, `cleanup.policy=delete`, `retention.ms=-1` и `retention.bytes=-1`: история сохраняется до явного сброса стенда. Сервис предполагает один управляющий процесс Analytics. Ошибочные события требуют исправления источника и явного операторского решения; автоматического пропуска повреждённой истории нет.

`pnpm --filter @ticketing/analytics verify` проверяет настоящий HTTP, PostgreSQL, Redis и Kafka, включая пустые партиции, повторы, replay во время продаж, недоступный Redis и неудачный replay. Проверка создаёт собственные SQL schema, topic, consumer groups и ключи Redis и удаляет их после выполнения. Общие сервисы не останавливаются.

## Возвраты и CSV

`events` считает действующие заказы и билеты. `grossRevenue` — подтверждённые продажи, `refunds` — завершённые возвраты, `revenue` — разность. `daily` сохраняет исходные продажи на дне подтверждения, а возвраты записывает на дне завершения возврата. Дни определяются в UTC; дневная выручка может быть отрицательной.

Полный снимок события включает даты подтверждения, отмены и возврата, поэтому обратная доставка не меняет конечный итог. Старый `order.confirmed v1` нормализуется к первой ревизии. При обновлении старого стенда необходим `pnpm upgrade:state`: live-consumers не применяют новую логику к агрегатам прежнего формата.

`GET /internal/reports/orders.csv` требует служебный токен и `organizerId`; необязательны `from`, `to`, `eventId`. Поток использует отдельный пул из двух соединений и SQL-курсор с порциями по 500. Снимок фиксирует активное поколение для всей выгрузки. Отмена HTTP закрывает курсор; старые поколения не удаляются во время чтения.
