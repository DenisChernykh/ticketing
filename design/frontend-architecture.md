# Ticketing: решение по фронтенду и передача в разработку

Статус: утверждённое направление и технические примечания к макету Pen.
Этот этап создаёт макет и документацию; приложение, API и зависимости не изменены.

## Технология и границы

Одно приложение **Next.js App Router + React + TypeScript** в будущем `apps/web`.
Tailwind CSS задаёт оформление, shadcn/ui — доступные базовые компоненты,
TanStack Query — состояние запросов, пагинацию и обновление асинхронных результатов.
Next.js объединяет публичный каталог и интерактивные кабинеты в одной сборке.
Отдельный React SPA потребовал бы второй сборки и отдельной интеграции сессий.

Sales остаётся владельцем бизнес-правил, авторизации и публичного API.
Next.js отвечает за представление и фиксированный прокси к Sales; не подключается к БД,
Redis, брокерам, Analytics, Fulfillment или Payment mock напрямую.
Модули фронтенда группируются по функциям: каталог, заказы, мероприятия, отчёты.
Общие компоненты и HTTP-клиент используются обоими кабинетами.
Каталог получает серверный первый рендер; формы и кабинеты используют клиентские компоненты.
Роль определяет навигацию, но право на каждую операцию по-прежнему проверяет Sales.
Глобальная админка, учебная лаборатория и прогресс обучения в первый этап не входят.

## Маршруты и реальные контракты

В таблице API указан без браузерного префикса `/api`.

| Страница | Sales API и поведение |
| --- | --- |
| `/` | `GET /events?limit=20&cursor=…`; `items`, `nextCursor`; «Загрузить ещё» |
| `/events/[id]` | Предлагаемый `GET /events/:id`; `POST /orders` с `{eventId, quantity}` и `Idempotency-Key` |
| `/login` | `POST /auth/login` с email/password; ответ `{user, csrfToken}`; возврат на безопасный локальный путь |
| Общая сессия | `GET /auth/me`, `GET /auth/csrf`, `POST /auth/logout` |
| `/account/orders` | `GET /orders?limit=20&cursor=…`; список заказов без вложенного `payment` |
| `/account/orders/[id]` | `GET /orders/:id`, `POST /orders/:id/payments`, `POST /orders/:id/cancel`, `GET /orders/:id/tickets` |
| `/organizer/events` | `GET /organizer/events?limit=20&cursor=…`; дополнительные `sold`, `revenue` |
| `/organizer/events/new` | `POST /events`: `title`, `venue`, `startsAt`, `capacity`, `unitPrice` |
| `/organizer/events/[id]/edit` | Предлагаемый `GET /events/:id`; `PATCH /events/:id` с изменениями и текущей `version` |
| `/organizer/reports` | `GET /reports/events`, `/reports/daily`, `/reports/popular?limit=10`; CSV отдельным действием |

`GET /events/:id` — **будущее дополнение**, необходимое для прямых ссылок и конфликта редактирования.
Возвращает текущую модель `Event`: `id`, `organizerId`, `title`, `venue`, `startsAt`,
`version`, `capacity`, `available`, `unitPrice`, `currency`.
Некорректный UUID даёт `400 VALIDATION_FAILED`, корректный неизвестный — `404 EVENT_NOT_FOUND`.
Чтение публичное; право редактирования остаётся за владельцем в `PATCH`.
Не вводить описание, постер, категории, поиск, рассадку или регистрации: их нет в текущем API.

Суммы передаются целыми копейками RUB; UI форматирует рубли без вычислений с дробными деньгами.
Заказ содержит 1–100 билетов одного мероприятия; API проверяет наличие мест заново.
Форма цены переводит десятичный ввод рублей в целые копейки; дата отправляется ISO с часовым поясом.
Вместимость: 1–1 000 000; цена: 1–100 000 000 коп.; название до 200, площадка до 300 символов.
Даты событий показываются в поясе пользователя; выбранный пояс виден рядом с датой.
JSON-отчёты не принимают период; нельзя изображать общий фильтр дат как работающий.
CSV: `GET /reports/orders.csv?from=YYYY-MM-DD&to=YYYY-MM-DD&eventId=…`;
`eventId` необязателен, обе даты включены и относятся к подтверждению заказа в UTC.
Дневные отчёты также используют UTC; `revenue = grossRevenue - refunds` может быть отрицательной.
Данные отчётов обновляются асинхронно; не обещать мгновенное совпадение с Sales.

## Интеграция, сессии и получение данных

Будущий браузерный адрес локально: `http://127.0.0.1:3000`; запросы только в `/api/*`.
Прокси удаляет `/api` и передаёт разрешённые маршруты таблицы в фиксированный
серверный `SALES_API_URL=http://127.0.0.1:3110`; пользователь не задаёт upstream URL.
Для CSV сохраняются потоковая передача, заголовки файла и отмена upstream при отключении клиента.
Прокси передаёт `Cookie`, `Set-Cookie`, `Origin`, `Sec-Fetch-Site`, `X-CSRF-Token`,
`Idempotency-Key`, HTTP-статус, problem JSON, `X-Trace-Id`; внутренний токен браузеру не нужен.
Заголовки Origin и Sec-Fetch-Site не переписываются для обхода защиты.

**Будущая настройка Sales:** `PUBLIC_APP_ORIGIN=http://127.0.0.1:3000` локально,
точный HTTPS origin фронтенда в production, без пути, wildcard и завершающего `/`.
Сейчас `assertOrigin` сравнивает Origin с протоколом и Host самого Sales,
поэтому проксирование без доработки проверки Origin недостаточно.
Присутствующий Origin разрешён только при точном совпадении с транспортным
`protocol://Host` Sales **или** настроенным `PUBLIC_APP_ORIGIN`; прямой Swagger продолжает работать.
Без `PUBLIC_APP_ORIGIN` остаётся только текущее сравнение с транспортным origin.
Сохранить запрет `Sec-Fetch-Site: cross-site` и обязательный CSRF для мутаций с сессией.
Отсутствующий Origin остаётся допустимым для HTTP-клиентов по существующему контракту;
некорректную конфигурацию origin отклонять при запуске. CORS для другого origin не требуется.

Cookie `ticketing_session` остаётся HttpOnly, Path=/, SameSite=Lax; Secure включается для HTTPS.
CSRF хранится в памяти: из ответа login, после перезагрузки из `/auth/csrf`.
Изменения и logout отправляют `X-CSRF-Token`; login проверяет Origin, но ещё не требует CSRF.
При 401 очистить пользовательский query cache и вернуть ко входу с локальным return path;
при logout также очистить CSRF. Не хранить cookie-сессию или пароли в localStorage.
Серверные fetch каталога и приватных данных используют `cache: 'no-store'`;
приватные ответы прокси — `Cache-Control: private, no-store`, без общего кеширования.
После мутаций обновлять затронутый заказ, списки и остатки; серверный ответ всегда определяет итог.
Обновлять видимую деталь раз в 2 секунды при `reserved`, `pending`, `refund_pending`;
доставку — пока её результат `pending`. При скрытой вкладке опрос приостанавливается,
при возврате/восстановлении сети данные перечитываются; терминальные состояния не опрашиваются.
При 503 сохранять последнее известное состояние и показывать проблему связи;
повтор чтения замедлять до 10 секунд, не запускать повторные мутации автоматически.

## Асинхронные состояния и ошибки

| Независимый результат | Значения и трактовка |
| --- | --- |
| Заказ `status` | `reserved`, `confirmed`, `cancelled`, `expired` |
| `payment.status` детали | `not_started`, `pending`, `succeeded`, `failed`, `refund_pending`, `refunded`; до чтения результат неизвестен |
| `/tickets.status` | `pending`, `completed`, `failed`, `cancelled`; относится к билетам **и уведомлению**, а не только билетам |

После `202` на оплату показывать ожидание; готовность билетов брать из отдельного запроса.
Уже полученные валидные билеты показывать даже при ожидающем уведомлении; не обещать PDF, которого нет в API.
При отмене/истечении билеты недействительны; поздняя оплата приводит к возврату, не восстановлению заказа.
Таймер строится по `expiresAt`; при нуле блокировать оплату и перечитать сервер, не менять статус самостоятельно.
Ключ бронирования создаётся на попытку покупки и сохраняется вместе с неизменным телом до выяснения исхода;
после потери ответа повторять тот же ключ и затем читать заказ отдельным GET.
При `CURSOR_STALE` объяснить обновление каталога и начать пагинацию с первой страницы без дублей.
При `EVENT_VERSION_CONFLICT` сохранить введённые поля, показать свежую версию для сравнения;
новый PATCH отправлять с актуальной version только после явного выбора пользователя.
Ошибки `application/problem+json` разбирать по `code`; `requestId` показывать в подробностях ошибки.
Для 403, 404, 409, 429 и 503 предусмотрены отдельные сообщения и допустимое следующее действие.

## Приёмка будущей реализации

- Прямая ссылка на событие и возврат после входа работают; оба кабинета защищены ролью и владельцем на Sales.
- Login/logout и мутации через `/api` и прямой Swagger проходят; чужой Origin и неверный CSRF отклоняются, cookie не видна JavaScript.
- Покупка, потеря ответа, повтор, истечение, отказ оплаты, выпуск билетов и отмена с возвратом проверены сквозным сценарием.
- `202`, доставка `pending/failed` и недоступность 503 дают разные экраны; поздняя оплата не возобновляет истёкший заказ.
- Две вкладки вызывают конфликт редактирования без потери ввода; курсор обновляется без повторов карточек.
- CSV скачивается с периодом UTC; суммы отчётов различают продажи, завершённые возвраты и выручку.
- Приватный кеш очищается при смене сессии; на 1440/390 px нет обрезаний, формы доступны с клавиатуры.
- Для реализации выполнить подходящие unit/integration и браузерные сценарии; для текущего документа достаточно сверки с контрактами.
